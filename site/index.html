How JevTO saves tokensMethod

It removes what the agent would skim, not what it needs.

Most command output is ceremony: hundreds of ... ok lines, progress redraws, regenerated lockfiles, log noise. An agent pays for every line it reads, and pays again each turn the output stays in context. JevTO decides line by line what to keep, and records why.

  1. 1

    Capture exactly

    The command runs with your permissions. Stdout, stderr, and the exit code are stored separately and hashed in a local store.

  2. 2

    Protect the facts

    Failures, assertions, panics, warnings, and exit status are marked protected. No rule and no model can drop them.

  3. 3

    Fold the ceremony

    Recognizers for Rust, Go, Python, Node, Jest/Vitest, and TAP test inventories, Cargo progress, lockfile and minified diffs, and long logs replace noise with a count and a gap marker.

  4. 4

    Recall on demand

    Each gap names a section. jevto recall ID --section … returns those bytes exactly. If the view would not be smaller, the original is delivered unchanged.

Optional: Jev, the decision layer.

Keyword rules can't tell which of 14 changed files matters, or that "how many times do we retry" is answered by fn default_retry_budget(). For search results, multi-file diffs, and long logs, an opt-in adaptive mode sends one bounded request (≤ 64 KiB, 4 s timeout, secret-filtered) to Jev, which ranks sections by meaning. Protected facts stay local and can't be dropped. Off by default; it needs an explicit policy file and a remote opt-in. Its live benchmark run is still pending.

BenchmarksReproducible

Fewer tokens only count if the answer survives.

23 scenarios in three suites (dev, a holdout written after the rules froze, and vocabulary-mismatch cases), each command routed through the tool's own Claude Code hook, so each tool handles exactly what it would in practice. Tokens are bytes ÷ 4 for one command's output. A fact is something the agent needs to finish the task (the failing test, the assertion, the relevant commit) visible without a recall.

A 98% smaller test result is a much smaller session win.

Same task on two agents: implement a small parser, verify with a 260-test unittest -v suite, 15 hidden holdout cases. Each run starts from a fresh copy of the repository, three runs per arm. The command output shrinks 50×, but the system prompt, file reads, and the agent's own reasoning still dominate the bill.

What the numbers do and don't say.

Where it wins

  • Test runners RTK doesn't route (Python, Node) and long logs: −69% to −98% with every fact kept, on scenarios written after the rules froze too.
  • Lockfile-heavy diffs: 11,484 → 120 tokens; a 14-file mechanical refactor shows the edit once and the real fix in full.
  • Keeps facts that truncation drops: the git log commit and the multi-file fix line.
  • In whole sessions it was the cheapest arm on both agents, with equal outcomes.

Where it doesn't

  • RTK is tighter on Rust and Go failures and tiny passing runs.
  • Deterministic mode misses a search answer that shares no words with the goal, and won't shrink a diff where every file is a distinct real change. The live Jev arm for those has not run yet.
  • Session savings are 3–31% depending on the metric, not 94%. Output is a small slice of a session.
  • n = 3 on one small task per agent. A Cursor pair had unequal outcomes. Indicative, not significant.

The benchmark scenarios were written by the JevTO author. They're generated from scratch by a committed script so anyone can rerun them, or add scenarios that JevTO handles badly.

The route is explicit.

Every installer previews first, applies only with --apply, backs up what it changes, and removes only its own entry. A failed hook leaves the command native. The Claude hook never sets a permission decision.

Local storagePrivacy

Output stays on your machine.

  • Deterministic mode makes no network requests and sends no telemetry.
  • Captures expire after 24 hours; the store is capped at 1 GiB.
  • Command arguments and environment variables aren't stored.
  • Jev sees only what an explicit policy allows, bounded and secret-filtered.

The store isn't encrypted at rest, and captured output can contain secrets. Review what you wrap.

Try it from source.

One binary, no account. The Claude Code installer shows what it would change and does nothing until you add --apply. jevto gain reports what was saved, from local receipts.

Agent-level harnesses for Claude Code, Codex, and Cursor live in benchmarks/.

C:\src\jevto>
cargo install --path crates/jevto-cli
jevto doctor

# Claude Code: preview, then apply
jevto init-claude-auto --workspace .
jevto init-claude-auto --workspace . --apply

# Any agent or shell
jevto run -- cargo test --workspace
jevto recall <capture-id>
jevto gain
